# 부꾸 프로젝트

불안한 순간을 응원과 디지털 부적으로 바꾸는 Android 모바일 애플리케이션.

## 1. 프로젝트 개요

부꾸는 사용자의 운세와 상황을 바탕으로 AI 맞춤 해석을 제공하고, 디지털 부적을 만들고 저장하거나 친구에게 전달할 수 있도록 돕는 앱이다.

3명의 팀원이 AI 기반 바이브코딩을 활용해 개발한다. 팀원이 이해할 수 있는 단순한 구조를 유지하며, Android 에뮬레이터와 실제 Android 기기에서 정상 동작하는 앱을 만드는 것을 목표로 한다.

이 README는 프로젝트 전체에 적용되는 기술 기준과 개발·협업 규칙을 관리한다. 개별 화면 정의와 기능명세는 `docs/`에서 관리한다.

## 2. 확정 기술 스택

| 구분 | 기술 및 도구 |

## 3. 개발 환경 기준

아래 값은 팀에서 합의한 공통 개발 환경 기준이다.

| 항목 | 기준 |
| --- | --- |
| Android Studio | Quail 4 \| 2026.1.4 이상 |
| JDK | 17 |
| Kotlin | 2.4.20 |
| Android Gradle Plugin (AGP) | 9.2.0 |
| Gradle | 9.4.1 |
| Compile SDK | 36 |
| Target SDK | 36 |
| Minimum SDK | 26 |

- JDK 17을 프로젝트 공통 기준으로 사용한다.
- AI는 Gradle, AGP, Kotlin, SDK 및 Compose 관련 버전이나 설정을 임의로 업그레이드하거나 다운그레이드하지 않는다.
- 버전 변경이 필요한 경우 변경 이유와 영향 범위를 먼저 설명하고 사용자 확인을 받는다.
- 실제 프로젝트 설정이 이 기준과 다르거나 호환성 문제가 발견되면, 차이를 알리고 사용자와 변경 방향을 확인한다.
- 승인된 환경 변경은 실제 프로젝트 설정과 이 README에 함께 반영한다.

## 4. 프로젝트 구조 원칙

1. 팀원이 이해할 수 있고 AI가 기존 코드를 읽고 수정하기 쉬운 단순한 구조를 유지한다.
2. 기능 구현에 필요하지 않은 구조를 미리 만들지 않는다.
3. 불필요한 라이브러리와 의존성(Dependency)을 추가하지 않는다.
4. 기존 프로젝트 구조와 코딩 방식을 우선한다.
5. 새로운 기술이나 구조를 도입할 때는 필요한 이유가 있어야 한다.
6. 이미 존재하는 기능과 공통 컴포넌트를 최대한 재사용한다.
7. 실제 Android 기기에서 정상 동작하는 것을 최종 기준으로 한다.

복잡한 Clean Architecture, 별도의 Domain Layer, UseCase 등은 실제 필요성이 발생하기 전에는 도입하지 않는다.

## 5. 기본 시스템 구조

### 전체 구조

```text
Android App
    ↕ REST API
FastAPI Backend (Render)
    ├── Supabase PostgreSQL
    ├── Supabase Storage
    └── External LLM API
```

- Android 앱은 FastAPI 서버와 REST API 방식으로 통신한다.
- FastAPI는 데이터베이스, 저장소 및 외부 LLM API와의 연동을 담당한다.
- Android 앱에서 LLM API를 직접 호출하지 않는다.
- LLM API Key와 기타 서버용 Secret Key는 FastAPI 서버에서 관리한다.

### Android 내부 구조

```text
Jetpack Compose UI
        ↕
     ViewModel
        ↕
    Data / API
        ↕
 FastAPI Backend
```

- Jetpack Compose는 화면 표시와 사용자 입력을 담당한다.
- ViewModel은 화면에서 사용하는 데이터와 상태를 관리한다.
- Data / API는 데이터 접근과 서버 통신을 담당한다.
- 화면 코드는 가능한 한 단순하게 유지한다.

## 6. docs/ 문서 사용 규칙

개별 화면과 기능의 세부 요구사항은 루트 README에 나열하지 않고 `docs/`에서 관리한다. 해당 기능을 개발할 때 사용할 화면 정의와 기능명세의 간략한 내용을 문서로 작성한다.

파일 구성 예시:

```text
docs/
├── scr-1-my-amulet.md
└── scr-2-friend-amulet.md
```

각 문서에는 해당 기능 개발에 필요한 내용을 담는다.

- 화면 목적과 주요 기능
- 사용자 입력과 행동
- 출력 결과
- 미정 사항과 주의 사항

기능 개발 전에는 반드시 관련 `docs/` 문서를 읽는다. 관련 문서가 여러 개라면 필요한 문서를 모두 확인한다. 문서나 현재 코드만으로 요구사항을 확정할 수 없는 부분은 임의로 결정하지 않고 사용자에게 확인한다.

프로젝트 공통 기준은 README에, 화면별·기능별 요구사항은 관련 `docs/` 문서에 유지한다.

## 7. AI 개발 시작 절차

AI는 요청을 받자마자 코드를 작성하거나 수정하지 않는다. 모든 기능 개발과 코드 수정은 다음 순서로 진행한다.

### 1단계: README, 관련 문서 및 현재 코드 확인

다음 내용을 먼저 읽는다.

1. 루트 `README.md`
2. 작업 대상과 관련된 `docs/` 문서
3. 현재 프로젝트 디렉터리 구조
4. 현재 구현된 코드와 설정

### 2단계: 현재 상태 파악

이미 구현된 기능, 수정할 코드, 새로 필요한 코드, 재사용할 수 있는 부분 및 아직 결정되지 않은 사항을 파악한다. 확인하지 못한 내용을 사실처럼 말하거나 임의로 확정하지 않는다.

### 3단계: 개발 계획 설명

코드를 수정하기 전에 사용자에게 무엇을 어떻게 만들 것인지 쉽고 짧게 설명한다.

- 이번 작업에서 구현하거나 변경할 내용
- 기존 코드에서 활용할 부분과 주요 변경 범위
- 동작을 확인할 방법
- 사용자 판단이 필요한 사항이 있다면 해당 내용

개발자가 아닌 팀원도 이해할 수 있도록 설명하고, 불필요하게 복잡한 기술 용어나 긴 설계 설명은 피한다.

### 4단계: 사용자 확인 후 개발

설명한 개발 계획에 대해 사용자가 확인한 뒤 구현을 시작한다. 요구사항이 불명확하거나 중요한 결정이 필요한 경우 먼저 확인한다. 작업 중 확인받은 범위를 넘어서는 변경이 필요해지면 변경 이유와 계획을 다시 설명하고 확인받는다.

## 8. AI 코드 수정 규칙

- 기존 코드를 먼저 읽고 수정한다.
- Jetpack Compose와 ViewModel 중심의 간단한 MVVM 구조를 유지한다.
- 새로운 프로젝트 구조를 임의로 만들지 않는다.
- 기존 Gradle 설정 및 개발 환경 버전을 임의로 변경하지 않는다.
- 기존 코드 스타일과 구조를 우선한다.
- 새로운 의존성은 꼭 필요한 경우에만 추가하고 이유를 설명한다.
- 기존 기능을 이유 없이 다시 구현하지 않는다.
- 하나의 기능을 구현하기 위해 프로젝트 전체 구조를 변경하지 않는다.
- 과도한 추상화나 복잡한 디자인 패턴을 사용하지 않는다.
- 이미 존재하는 기능과 컴포넌트를 최대한 재사용한다.
- 확인받은 개발 계획과 관련된 범위 안에서 필요한 코드를 수정한다.

## 9. 개발 완료 후 보고

작업이 끝나면 AI는 다음 내용을 간단하게 정리한다.

1. 구현하거나 변경한 내용
2. 새로 생성한 파일과 수정한 파일
3. 추가한 의존성과 그 이유 — 추가한 경우
4. 실행 또는 테스트 방법과 실제 확인 결과
5. 남아 있는 문제, 미정 사항 및 확인하지 못한 부분

실행하거나 테스트하지 못한 내용은 확인 완료로 보고하지 않는다. 프로젝트 전체에 영향을 주는 새로운 기술적 결정이 생긴 경우에는 README 또는 별도의 공통 문서 업데이트를 제안한다.

## 10. 개발 방식

전체 앱을 한 번에 구현하지 않고 기능 단위로 개발한다. 각 기능은 다음 순서로 완성한다.

```text
디자인 확정
    ↓
Frontend / Backend 개발
    ↓
API 연동
    ↓
통합 테스트
    ↓
실제 Android 기기 테스트
    ↓
기능 완료
```

하나의 기능이 실제 앱에서 정상적으로 동작하면 완료로 판단한다. 임시 데이터만 연결된 상태와 실제 API 연동이 완료된 상태를 구분한다. 완벽한 설계를 미리 만드는 것보다 실행 가능한 기능을 만들고 필요한 구조를 개발 과정에서 추가하는 것을 우선한다.

## 12. Git 작업 원칙

- `main` 브랜치는 실행 가능한 상태를 유지한다.
- 기능 개발은 별도의 브랜치에서 진행한다.
- 변경 내용을 확인하고 Pull Request를 통해 검토한 뒤 `main`에 병합한다.

브랜치 이름 예시:

```text
feature/fortune-ui
feature/fortune-api
feature/amulet
```

기본 작업 흐름:

```text
Branch 생성 → 개발 → Commit → Push → Pull Request → 확인 → main Merge
```

API Key와 Secret 값은 GitHub에 업로드하지 않는다. Backend의 로컬 환경 변수는 `.env`로 관리하고 Git 추적에서 제외한다. 저장소에는 실제 비밀값 없이 필요한 환경 변수 항목을 안내하는 `.env.example`을 관리한다.
